13  Running an established pipeline

13.1 Learning Objectives

Learning Objectives:
Run an existing Nextflow Pipeline
Monitor pipeline progress
Evaluate the pipeline run statistics
Identify components of a pipeline and its outputs

In this chapter we’re going to explore the workflow language Nextflow from the perspective of a pipeline that has already been developed. We’re going to look at the rnaseq pipeline from the nf-core project, a “global community effort to collect a curated set of open-source analysis pipelines built using Nextflow”.

The general philosophy of nf-core is to develop and maintain a set of general, reusable, portable pipelines applicable to particular types of data analysis. For a given application, such as bulk RNA-seq, or genome assembly they aim to create a single pipeline which may take many different types of data as input, and allow different pieces of software to be specified for particular steps in the workflow. This contrasts with other pipelines you might find out in the wild, which may be developed to execute a very focused analysis, or tailored to a specific resource.

In this chapter the goal is to see how Nextflow works, how it integrates with SLURM, and some ways to explore how it ran. In the next chapter you will look at writing actual nextflow code.

13.2 The data

To provide a familiar backdrop, we’re going to revisit the test data set from ISG5311: the data on the transcriptomic basis of pollution tolerance in Fundulus heteroclitus.

Reid, Noah M., et al. “The genomic landscape of rapid repeated evolutionary adaptation to toxic pollution in wild fish.” Science 354.6317 (2016): 1305-1308.

To review, this study compared 4 killifish populations that have evolved tolerance to a class of very nasty industrial pollutants (dioxin-like compounds) and 4 that are sensitive. The transcriptomic part of the study was an experiment exposing fish embryos to a model toxicant, PCB-126 and a control (DMSO) and sequencing RNA extracted from the whole RNA.

As in ISG5311, we’re going to work with just one pair of populations, Elizabeth River and King’s Creek. As usual, you can find a git repository with scripts for this chapter here. Clone it to get started.

Because this is all old hat by now, we won’t go over all the details but you’ll need:

  • The raw fastq files
  • The reference genome
  • The reference genome GTF file.

To get those you can run scripts/01_getData/01_downloadSRA.sh and scripts/01_getData/02_getGenome.sh. They are essentially the same scripts for downloading the same data we used last semester. If you’ve still got that data around (though you’ve probably deleted it due to space constraints at this point), you could just symlink it to the appropriate directories instead of running the scripts.

13.3 The rnaseq pipeline

If you visit the rnaseq page, you’ll find details on what it does and how it runs. Note that the main end point is the count data (and a lot of QC). This pipeline does not do differential expression analysis or other downstream analyses of RNA-seq data. If you check out their very nice “subway” map of the pipeline you can get a sense of how complex it is.

You will likely recognize some of the steps here. A downside of a pipeline like this is that it’s not always entirely clear which options you should choose, or where the particular outputs you want will be located. For this pipeline, there are at least four paths to generating counts (2 full alignment and quantification options and 2 pseudo-aligment and quantification options).

Note

In this case, the option to quantify using HISAT2 mappings and htseq-count as we did last semester is not even an option. In fact, the pipeline docs suggest it is incorrect to quantify in this way (and they provide a few citations). The pipeline instead requires that data be mapped against a transcriptome (either provided, inferred from the GTF file, or assembled from the mapped reads using stringtie). For gene-level quantification, it combines counts across transcripts. While there is some evidence this can be beneficial, it’s not not at all clear that this more complex approach would be superior for a non-model organism with very little evidence backing the existence of multiple transcripts.

13.4 Running the pipeline

We’re going to run the pipeline using the default approach. It will align to the reference genome using STAR, project the alignments to the transcriptome implied by the GTF annotation file, and quantify expression using salmon.

Here we provide a sample name, paths to the input data, and the strandedness of the library (“auto” means infer from the data). If you have multiple sequence runs per sample, you can put them on separate lines with the same sample name and they’ll be combined.

Let’s look at the script scripts/02_runNF/01_runNF.sh and then submit it. First, the header:

#!/bin/bash
#SBATCH --job-name=runNF
#SBATCH -n 1
#SBATCH -N 1
#SBATCH -c 2
#SBATCH --mem=10G
#SBATCH --partition=general
#SBATCH --qos=general
#SBATCH --mail-type=ALL
#SBATCH --mail-user=first.last@uconn.edu
#SBATCH -o %x_%j.out
#SBATCH -e %x_%j.err

Pretty typical SLURM header. You will probably notice that these resources seem really skimpy. That’s because we are going to tell Nextflow to use SLURM as its executor. That means this job will only manage the pipeline. All the heavy computing will be submitted by this job as separate batch jobs. It will monitor those jobs and when they complete, submit subsequent jobs that depend on them.

We’ll see more about how that works in a moment, but for now what this means is that only pipeline runs with huge numbers of tasks to manage need more resources than this.

As usual, we’re going to load our software module next and create an output directory. We’re going to cd to that directory to run nextflow just to keep things cleaner.

module load nextflow/24.10.5

OUTDIR=../../results/nfcoreRNAseq
mkdir -p ${OUTDIR}

cd ${OUTDIR}

And finally we run the pipeline:

SAMPLESHEET=../../metadata/samplesheet.csv
GENOME=../../genome/Fundulus_heteroclitus.Fundulus_heteroclitus-3.0.2.dna_sm.toplevel.fa
GTF=../../genome/Fundulus_heteroclitus.Fundulus_heteroclitus-3.0.2.112.gtf

# use xanadu profile from: https://nf-co.re/configs/xanadu/
nextflow run nf-core/rnaseq \
    --input ${SAMPLESHEET} \
    --outdir out \
    --fasta ${GENOME} \
    --gtf ${GTF} \
    -profile xanadu \
    -with-trace trace.txt \
    -with-report report.html \
    -with-timeline timeline.html \
    -with-dag dag.png

We provide our sample sheet, the name of an output directory (out), our genome, GTF file, and some options.

The most important option here is -profile xanadu. This is an institutional profile uploaded to nf-core. When we use this option, nextflow goes to the nf-core website and grabs this configuration file. The main thing this configuration file does is tell nextflow how SLURM works on Xanadu. It says, for example, that it should never request more than 2TB of memory or 64 CPUs. It says it should use SLURM to submit tasks, and which partition and QOS to use, depending on the memory required by the task. It also tells nextflow to wait 2 seconds in between job submissions (SLURM can be overwhelmed by thousands of simultaneous submissions).

Importantly, the configuration says that nextflow should use Singularity to run software in the pipeline. For this nf-core pipeline, that means that Nextflow will automatically download singularity containers and run each task using those containers. So we don’t need to have everything the pipeline needs installed locally already. That would be a huge challenge for a pipeline like this, which may depend on very specific software version numbers.

The -with-* options all ask nextflow to produce some files summarizing the run. They can be pretty helpful in understanding the resource usage of each step.

13.4.1 Monitoring the pipeline

Go ahead and submit this job. Watch it for a while. Keep typing squeue -u $USER and checking the runNF_<jobID>.out file.

It should first spit out some of the basic input parameters. It will also give you a “run name” like this:

These are tasks in the pipeline that need to be run. 0 of 20 indicates that the task will be run 20 times (in this case on each of our 20 samples). Unfortunately, the task names are pretty long and get truncated in this view, so it’s not exactly clear what they are (more in a moment).

The bits inside the brackets, e.g. d4/f72bbe refer to subdirectories of the work directory where a given task is being executed. This bit refers to: results/nfcoreRNAseq/work/d4/f72bbe8221d954524068746746c00a/. The f72bbe is just the first few letters of f72bbe8221d954524068746746c00a. If you keep looking at squeue -u $USER you should see tons of jobs being submitted by nextflow. Some will go very quickly, others will take a few minutes. If enough resources are available, the entire pipeline should complete in about two hours.

A couple points you should be aware of:

  • If a task gets killed, nextflow has options to have it automatically restarted a few times (they’re enabled in this pipeline).
  • If the entire pipeline gets killed (e.g. if the main job for stupefied_brenner had been interrupted) you can add the option -resume to the nextflow call, and it will start back up where it left off on the last run, using any completed intermediate results.
  • If you don’t do -resume everything will be computed fresh.

It’s tab-delimited, so a bit hard to follow here, but this gives a lot of useful info for each task in the pipeline. It also gives the “hash” that can be used to check out the work directory for each step.

Next, you should download and look at the html and png files locally.

  • dag.png: The pipeline can be thought of as a “directed acyclic graph” (DAG). Each task in the pipeline (e.g. alignment) is a node, and edges connect the nodes directionally to define the flow of data through the whole thing. Open dag.png in an image viewer to get a sense of how complex this pipeline is.
  • timeline.html: this file is a visual summary of the timeline of the pipeline run. it gives the relative start time, wall time used, and memory usage for each task in the pipeline.
  • report.hml: this file summarizes tasks by task type (and also has all the info from trace.txt plus some). That last table with the trace info also lists the singularity container used, and the SLURM job ID (column “native_id”).

Finally, we have .nextflow.log. This file contains information that largely overlaps with all the above stuff. Importantly it’s the easiest place to find the SLURM job id for a given task, aside from report.html. Just grep the hash (e.g. a9/178e26 and look for jobID)

13.6 The work directory

The work directory is a bit of a bear. It’s where all the individual tasks are completed. Individual task “hashes” like a9/178e26 refer to subdirectories in work, like work/a9/178e26fcb8a8dbb490d3f90b409c70/. What’s in these subdirectories? Let’s examine this one, a salmon quantification task for sample SRR12475449 (your path will be different, but you should be able to figure out the directory from trace.txt or .nextflow.log).

Notice there are some dot-files (e.g. .command.*) and some input and output files. The way nextflow works is that for each task a new work directory is created. All the necessary input files (often generated by previous steps) are symlinked into the directory. So here we’ve got our GTF file, our transcriptome fasta (inferred from the GTF) and our transcriptome-aligned BAM file as input. Symlinking puts all the necessary files in this work directory. Then scripts, intended to be run in this directory are created and run.

The .command.* files are pretty important.

  • .command.sh is the actual program script. When things are going wrong, it’s often useful to look at this.
  • .command.run is the SLURM batch script used to run .command.sh. It’s rarely helpful to look at this as it contains a large amount of challenging shell script.
  • .command.out and .command.err. The standard out and standard error files. Sometimes these can be pretty helpful to look at.

The core of .command.sh is our program call, in this case:

salmon quant \
    --geneMap Fundulus_heteroclitus.Fundulus_heteroclitus-3.0.2.dna_sm.toplevel.filtered.gtf \
    --threads 6 \
    --libType=IU \
    -t genome.transcripts.fa \
    -a SRR12475449.Aligned.toTranscriptome.out.bam \
     \
    -o SRR12475449

We also have our output. In this case it’s mainly the directory SRR12475449. It contains the files with gene and transcript-level expression profiles (along with some other info). Ultimately this directory is published to the output directory (out/star_salmon/SRR12475449).

Warning

After a single pipeline run there are something like 740 work subdirectories here, each containing at least 10 files. Every time you re-run the pipeline it will create new work subdirectories. If you decide you want to use a different parameter, you will get a whole new set of work subdirectories. If you cancel the pipeline run and restart without -resume you will get new work subdirectories. Furthermore, each of the files in the output directory also exist in the work directory. They were simply copied from work to out. And the intermediate files created by each step in the pipeline are not cleaned up by default.

All this is to say nextflow can create a huge number of files and use a ton of space. It’s a good idea to delete the work directory as soon as is reasonable. Sometimes there will be so many files to remove it will take an hour or more to delete it. For linux, removing large numbers of tiny files is much harder than removing a small number of very big files, so nextflow work directories can be a real annoyance.

13.7 The pipeline code

When we ran nextflow run nf-core/rnaseq <...> we didn’t actually point to a local copy of the pipeline code itself. nf-core/rnaseq is by default interpreted as a GitHub user/repository (e.g. http://github.com/nf-core/rnaseq). The pipeline code is then downloaded and stored in a hidden directory in your $HOME: ~/.nextflow/assets/nf-core/rnaseq/. For subsequent runs of the pipeline, that pipeline will be run. It’s possible to specify versions of the pipeline, or force the code to be updated to the latest.

For rnaseq, the actual pipeline directory looks like this:

main.nf is the starting point. Other key parts of the pipeline that define its structure are in workflows/, submodules/ and modules/. We won’t get into this in much detail now, but the basic building blocks of a nextflow pipeline are the modules. Let’s go look at the salmon quantification module that built the work directory we examined above.

It can be found here modules/nf-core/salmon/quant/main.nf

There’s a lot there because nf-core pipelines are fairly complex. But the key components are the input: block output: block and the actual code, a multi-line code block bounded by """. The key part of the code block, corresponding to the section of .command.sh that we examined above is this:

    salmon quant \\
        --geneMap $gtf \\
        --threads $task.cpus \\
        --libType=$strandedness \\
        $reference \\
        $input_reads \\
        $args \\
        -o $prefix

You can see that this mirrors how we have been organizing code and using variables to both make it easier to read, and reuse in loops or arrays.

13.8 The containers

Finally, we mentioned above that each program in this run was run inside a container. Where are those containers stored? On Xanadu we have set up a shared nextflow container cache directory: /isg/shared/databases/nfx_singularity_cache/. You may have noticed that defined in the institutional profile.

In the module file above, the container URL is listed as https://depot.galaxyproject.org/singularity/salmon:1.10.3--h6dccd9a_2 and we find the corresponding container /isg/shared/databases/nfx_singularity_cache/depot.galaxyproject.org-singularity-salmon-1.10.3--h6dccd9a_2.img.

13.9 Conclusion

In essence, nextflow boils down to a convenient way to automatically write, run, monitor, and summarize a collection of scripts that make up a workflow. Hopefully at this point in the course, you can see how this mirrors in many ways our strategy for organizing code and results in a project directory.

Whether doing an analysis yourself, running a pre-existing pipeline, or developing a formal pipeline from scratch is optimal is extremely context dependent. Prepackaged, containerized pipelines like those from nf-core can be fantastically convenient. If you don’t know what you’re doing and run into trouble, however, the complexity can make them challenging to understand and troubleshoot. They may also come with design choices built in that are suboptimal for your particular situation.
